## What it catches

The workbench flags deprecated authentication in code samples before it reaches production docs, and in CI it blocks a GitHub pull request that fails the check.

## The problem

In our developer docs, errors kept getting through. Code examples used deprecated patterns, like Basic Auth where the API now expects tokens, and writers cited the wrong facts, like port 80 when the API listens on 8089. Holding one consistent voice across many contributors by hand was also out of reach.

A linter catches syntax, and none of these are syntax errors. The first two are errors of fact, and catching them takes a tool that knows the platform.

## How it works

Every draft goes through a router that sends it to two engines.

The logic engine uses MCP to connect to the live API specification. It looks up the parameters the draft mentions, checks ports, versions, and methods, and runs a security scan on the code.

The style engine uses retrieval. It pulls the relevant rules from our PDF style guide out of a vector database, then checks voice and terminology against them.

Both engines feed one diff generator. What comes out is a corrected draft, a visual diff of every change, a log that tags each fix as logic, security, or style, and a comment ready to post on the pull request.

## Trying it

I built the front end in Streamlit and the orchestration in LangChain. The prototype runs on sample Splunk Enterprise data. You pick the product, paste a draft that uses port 80 and Basic Auth, and run the audit. The workbench returns the fixed code, a newer version number where the draft named a retired one, and a line in the log explaining each change.

## What it was for

I built it so the expensive part of review, checking facts, would move to the tool. A reviewer would still read every page, without having to go look up the port.
